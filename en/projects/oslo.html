Forecasting bike availability in Oslo

One-hour forecasts of the number of bikes available at Oslo’s 271 bike-sharing stations, based on 1.96 million records combined with weather data.

TypeBig Data & Machine Learning challenge (4th year)
TeamTwo students
Period2025 – 2026
Data1.96 M records · 271 stations

Context

This challenge combined two ESIROI courses: large-scale data systems and machine learning. The data come from Oslo’s bike-sharing service, which publishes the state of every station every three minutes, and from hourly weather records (Open-Meteo), from January to November 2025.

The need is practical: an operator has to know which stations will empty or fill up within the hour to plan bike redistribution.

Objectives

  • Deploy a distributed HDFS / Spark cluster.
  • Build an ETL pipeline with Spark, from the APIs to Parquet files.
  • Analyse usage by hour, day, season, weather and station.
  • Predict, for each station, the number of bikes available one hour later.

Three-phase architecture

  • Infrastructure : a 4-VM cluster (1 NameNode, 3 DataNodes), HDFS replication ×3, Spark 3.5. Distributed storage and processing were validated with dedicated tests.
  • ETL pipeline : extraction from the station API (JSON) and the weather API (CSV), parsing a nested JSON field with an explicit schema, aligning records to the hour, then joining them with the weather data. The full pipeline runs in 1 min 42 s.
  • Machine learning : 58 engineered features (past values from 1 to 24 h, rolling averages, cyclical encoding of hour and day, station profile, weather interactions) and a 70 / 15 / 15 chronological split so that no information leaks from the future into the past.

What the data show

  • Stations are emptiest around 3 pm, 4 pm and 11 pm, and fullest between 3 am and 6 am.
  • At weekends, 6% more bikes remain available on average.
  • When it rains, 5.7% more bikes stay docked: people ride less.
  • The distribution is bimodal: many stations are either nearly empty or nearly full.

Choosing the model

A first Random Forest reached an R² of 0.85 in training but only 0.48 on test data: it was learning noise. We switched to XGBoost with strong regularisation (shallower trees, a smaller learning rate, L1 and L2 penalties, early stopping), which halved the gap between training and test (from 0.15 to 0.09).

Results

  • On test data, forecasts are off by an average of 3.02 bikes from the actual count (RMSE 5.25; R² 0.47).
  • The most useful features are rolling averages over 3 to 6 hours and the number of bikes one hour earlier.
  • Station by station, the model beats a simple average on 154 of the 271 stations. Highly irregular stations (tourism, events) remain poorly predicted.

Limitations and next steps

  • More than half of the variation remains unexplained: one-off events, very local weather, individual behaviour.
  • Nearly empty stations make the relative error high, even when the gap in number of bikes is small.
  • Next steps: one model per station type, adding public holidays and events, real-time processing with Spark Structured Streaming. A production architecture was proposed but not deployed.

What I learned

I learned to turn a score into a concrete decision: for a nearly empty station, a three-bike gap can change whether it gets restocked.

The Random Forest also showed me that a good training score proves nothing until it is confirmed on unseen data.
